# 記事ブループリント（構成・SEO・出力）

## 記事の目的（最優先・全記事共通）

**この「実践知」メディアの記事は、最終的に受注（無料相談・開発の問い合わせ）につながることを目的とする。** ただの考察・トレンド解説で終わらせない。各記事は次の3つを同時に満たす：

1. **価値提供** — 読者（発注を検討する経営者・事業責任者）の実務課題に役立つ具体を渡す。
2. **開発力の証明** — 自社プロダクト（DIFFsense / MERKI / XDraft / さて。）の**開発・運営の実体験を一次情報として語る**。「私たちは実際にこう判断し、こう作り、こうなった」という現場の知見が、そのまま「この会社に頼めば本格的なものが現実的なコストで作れる」という信頼の証明になる。
3. **相談への接続** — 信頼を作ったうえで、押し付けずに相談導線へつなぐ（下記CTA設計）。

**書く前に毎回自問する：「この記事は、読者が私たちに発注したくなる理由を1つでも作れているか？」** 答えがNoなら、自社の開発経験・判断・数字（出せる範囲で）を足して、考察を実践知に変える。

営業色を出しすぎない。先に価値と実体験で信頼を作り、相談はその自然な帰結として置く。煽り・誇大・捏造は逆効果。

## 記事の標準構成

1,800〜3,000字程度を目安。実体験ベースのストーリー型で、読者が課題を解決しつつ自然にSPACE GLEAMを想起する流れを作る。

1. **導入** — 読者の具体的な困りごと、または開発・運営でよくある状況を提示して引き込む。結論の予告を1文。（短い段落で改行多め）
2. **本論（`##` 見出しを3〜5本）** — 各見出しの下を `###` で細分化。結論→理由→具体例（実体験）→学び の順。要点は太字でメリハリ（brand-voice.md の太字ルール）。
3. **実務への落とし込み** — 「では何から始めるか」を読者が動ける粒度で。
4. **まとめ** — 要点を簡潔に再掲。説教くさくしない。
5. **CTA** — 自社プロダクトまたは相談導線へ自然に接続。

### Markdown記法
- 見出しは `##`（大）/ `###`（小）。記事タイトル自体はfrontmatterの title に入るので本文では `#` を使わない。
- 段落は空行区切り。**一文ごと〜数文ごとに改行**して余白を作る（既存記事のスタイル）。
- 箇条書きは `- `、手順は `1. `。
- 強調は `**...**`。要点の短い語句のみ、1段落1か所目安。

## 出力形式（納品の正）

**frontmatter付きMarkdown、1記事1ファイル。** 自社サイトへのデプロイにそのまま流す。

frontmatter（記事冒頭、`---` で挟む）：

```
---
title: "記事タイトル"
slug: "url-slug"
description: "記事の概要（120字程度・メタディスクリプション兼用）"
---
```

その下に本文Markdown。
- `slug` は英数字とハイフンのみ。日本語タイトルから内容を表す短い英語スラッグを作る。
- `description` ＝ 社長の言う「概要」。検索結果でクリックしたくなる便益を120字程度で。
- frontmatterのキー名（title / slug / description）はデフォルト。デプロイ側が別名（例: meta-description）を要求する場合は `scripts/build_markdown.py` の `FRONTMATTER_KEYS` を変えれば全記事に反映される。

## SEO方針

- **主要キーワードを1記事1つ。** タイトル・冒頭100字・見出しのいずれか・まとめに自然に配置。
- タイトルは32字前後、主要キーワードを前方に。便益が伝わる言い回し。
- `description` は120字程度でメタディスクリプション兼用。
- 共起語・関連語を本文に自然に散らす（不自然な詰め込みはしない）。
- 1テーマ＝1記事で検索意図を1つに絞る。

## CTA設計

押し付けがましさを避け、記事の流れの延長で自然に。各記事に最低1つ。MVP等のNG語はCTAでも使わない。

- テーマがプロダクト領域に近い → 該当プロダクトを名指しで紹介し、解決像を1〜2文＋リンク導線。
- テーマが汎用的 → 「無料相談」「受託開発・プロダクト開発の相談」への導線（本格開発を現実的なコストで、の核を1文）。

CTA文例（雛形・記事に合わせ調整）：
- 「契約書まわりの確認に時間を取られているなら、AIで要約・差分チェック・電子署名までを一本化するDIFFsenseが役に立つかもしれません。」
- 「『社内にエンジニアがいないけれど、本格的な仕組みを作りたい』——そんなときは、私たちにご相談ください。妥協のない実装を、現実的なコストで。」

## カテゴリ体系（実サイトのフィルタに準拠）

ブログのフィルタは次の5分類。各記事は主に1つの領域に寄せる：

- **AI** — 生成AI・LLM活用・AI導入
- **SaaS** — SaaS運営・プロダクト運用
- **Development** — 開発の進め方・技術的な知見・受託
- **Business** — 事業づくり・経営判断・コスト/投資対効果
- **Product** — 自社プロダクト（DIFFsense等）に関する解説

※frontmatterに category キーが必要かはデプロイ仕様による。現状の納品は title / slug / description の3メタ＋本文。カテゴリ分けが必要になったら build_markdown.py にキーを追加する。

## テーマの軸（ネタ出しの発想源）

既存記事と重複しない切り口を選ぶ。**自社プロダクトの開発・運営の実体験に紐づくものを最優先**（受注の証明になりやすく、他社が書けない一次情報になる）：

1. **自社プロダクトの開発の意思決定を物語る（最優先）** — 「DIFFsenseでなぜ差分比較から作ったか」「あえて削った機能と理由」「電子署名を内製に切り替えた判断」など。開発の苦労・選択・結果を具体で。読者は「ここまで考えて作る会社なら任せられる」と感じる。
2. **コスト／発注の不安に答える** — 「開発はいくらかかるか」「なぜAIで本格開発が現実的になったか」。自社の実例を交えると説得力が増す。
3. **エンジニア不在の事業者向け** — 「技術者がいなくてもDXを進める方法」「外注先の選び方」。
4. **生成AI活用の実務** — 業種別の活用例、よくある失敗、導入の順序。自社の実装経験を根拠に。
5. **業務領域別の課題解決** — 契約・法務、バックオフィス等（自社プロダクトに接続しやすい）。
6. **SaaS運営の実践知** — 運用・改善・継続の学び。自社プロダクトの運営から得た一次情報。

各テーマ案には「想定検索意図」「主要キーワード」「カテゴリ」「どの自社プロダクト経験を根拠に使うか」「誘導先プロダクト or 相談導線」をセットで添える。
